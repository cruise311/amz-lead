# amz-lead 合规指南

> **核心原则**：代码开源，数据不出库，合规由使用者自负。

---

## 1. 数据来源合规性

| 阶段 | 数据来源 | 合规依据 | 风险等级 |
|---|---|---|---|
| **采集** | Amazon 前台公开页面（BSR 榜单、店铺主页、商品页） | 公开信息抓取，不绕过登录、不破解加密、不采集买家隐私 | 低 |
| **还原** | 企查查/天眼查/探迹开放检索接口 | 使用者自备合规账号与额度，仅做模糊匹配，不存储原始工商数据 | 中 |
| **补号** | 探迹/天眼查/企查查批量解锁接口 | 使用者自备合规账号，**严禁转售/二次分发**原始号码数据 | 高 |

---

## 2. 法律风险边界

### ✅ 允许的行为
- 采集亚马逊前台公开的店铺名、BSR 排名、地址、价格、类目
- 用公开工商信息做模糊匹配，输出「置信度分层」
- 调用探迹/天眼查/企查查**合规账号**的开放接口做批量查询
- 将处理后的「评分/分层/标签」交付给下游业务系统

### ❌ 禁止的行为
- 绕过亚马逊登录态、验证码、反爬机制（本项目仅处理前台公开页）
- 存储、转售、分发探迹/天眼查/企查查返回的**原始手机号、身份证号、股东信息**
- 将补号结果直接作为「名单产品」按条出售（需走「数据不出库、只出评分」架构）
- 违反《个人信息保护法》《反电信网络诈骗法》《数据安全法》的任何用途

---

## 3. 合规架构建议

### 开源版（当前仓库）
```
采集 → 还原 → 评分 → [补号接口定义] → 使用者自行实现/对接自有账号
```
- 补号模块（`src/lookup/`）**仅提供接口封装**，不含账号、不含额度、不含数据存储
- 使用者需**自备合规账号**，自行承担数据使用合规责任

### 云服务版/企业版（商业化交付）
```
采集 → 还原 → 评分 → 补号（数据不出库） → 只输出：分层标签/评分/可外呼标记
                                                                    ↓
                                                         下游 CRM/外呼系统
```
- **数据不出库**：原始手机号仅在内存中完成「可外呼/不可外呼」判定，**不落盘、不返回 API**
- 仅向下游交付：`tier: "A级"`, `callable: true`, `confidence: 0.92` 等**脱敏标签**
- 完整审计日志：谁在什么时间查了什么主体、得到了什么标签
- 支持私有化部署：数据不出企业内网

## 4. 使用者合规清单（部署前必核）

- [ ] 确认采集目标仅为亚马逊前台公开页面
- [ ] 探迹/天眼查/企查查账号为**企业实名认证**，用途登记为「自身业务拓展」
- [ ] 未将补号原始数据（手机号、身份证号）写入任何日志、数据库、文件、API 响应
- [ ] 下游业务系统仅接收「分层标签/评分」，不接收原始敏感字段
- [ ] 建立数据访问审计日志，保留 ≥ 6 个月
- [ ] 指定数据保护负责人（DPO），制定数据泄露应急预案
- [ ] 定期（季度）开展合规自查，更新风险评估报告

## 5. 常见合规问答

**Q: 开源版能不能直接跑通补号？**
A: 代码能跑通，但**需要你自己填入合规账号**。我们不提供账号、不提供额度、不承担因账号违规导致的封号风险。

**Q: 我能不能把跑出来的名单卖给别人？**
A: **不能直接卖原始名单**。你可以卖「基于该名单的评分/分层/标签服务」，或卖「帮客户跑一遍流程的服务费」。核心原则：敏感数据不出库。

**Q: 亚马逊会不会起诉爬虫？**
A: 本项目仅采集**前台公开页面**，不绕过登录、不破解加密、遵守 `robots.txt`、内置限速与退避。但法律风险由使用者自负，建议咨询法务。

**Q: 如何应对《反电诈法》对「买卖公民个人信息」的打击？**
A: 严格执行「数据不出库、只出标签」架构。补号阶段在内存中完成「可外呼/不可外呼」判定，**原始号码不落盘、不返回、不传给下游**。这不属于「买卖/提供公民个人信息」。
